# Contributing

1. Создать issue с целью и критериями.
2. Создать `feature/<short-name>`.
3. Сделать несколько осмысленных коммитов.
4. Запустить `make verify` — должен пройти полностью.
5. Открыть PR (в описании — вывод `make verify`).
6. Получить review второго участника.
7. Исправить замечания.
8. Merge в `main`.

Нельзя коммитить `.env`/секреты, удалять тесты, отключать проверки или пушить незавершенную работу напрямую в `main`.

Первая принятая версия: `v0.1.0`.

## Правила проверок

Эти правила проверяются автоматически (`make policy` — первый шаг `make verify`,
а также хуки в `tests/conftest.py`):

1. **Пропуск тестов запрещён.** Нельзя использовать `@pytest.mark.skip`,
   `skipif`, `xfail`, `pytest.skip()`, `pytest.importorskip()`. Если тест
   пропущен или помечен xfail, прогон завершается ошибкой.
2. **Пороги не снижаются.** Минимальное покрытие — `fail_under = 85` в
   `pyproject.toml`, нижняя граница зашита в `scripts/check_policy.py`
   (`MIN_COVERAGE`). В `Makefile` и `addopts` запрещены `--cov-fail-under`,
   `--no-cov`, `--deselect`, `--ignore`.
3. **Исключения анализаторов — только с обоснованием.** Каждый
   `# noqa`, `# nosec`, `# pragma: no cover`, `# type: ignore` должен содержать
   пояснение после `--`, например:
   `from app import models  # noqa: F401 -- импорт регистрирует модели`.
   Для bandit пояснение отделяется вторым `#`: `# nosec B603 # -- причина`.
   Исключения в конфигурации (`[tool.ruff.lint] ignore`) тоже комментируются.
4. **Эквивалентные мутанты** помечаются `# no-mutate -- причина` только если
   изменение действительно не меняет поведение программы.
5. Любое изменение порогов, правил линтера или этих правил делается отдельным
   PR с обоснованием и одобрением второго участника.

## Правила контейнерного окружения (Lab 4)

Проверяются автоматически `make container-check` (`scripts/container_check.py`);
окружение с нарушениями не принимается.

1. **Запрещён `latest`** и образы без точной версии — в `Dockerfile` и в `docker-compose.yml`.
2. **Запрещён запуск от root**: `USER` в образе и `user:` у каждого сервиса Compose;
   фактические процессы контейнеров проверяются через `docker top`.
3. **Запрещено помещать секреты в образ и в репозиторий**: никаких паролей в `ENV`/`ARG`,
   `docker-compose.yml` содержит только ссылки `${...}`, значения — в `.env`
   (в `.gitignore`, исключён из контекста сборки белым списком `.dockerignore`).
4. **Запрещено отключать healthcheck** (`disable: true`, `NONE`) у долгоживущих сервисов.
5. **Запрещено публиковать лишние порты**: наружу открыт только порт nginx (8080);
   порты БД и приложения не публикуются.
6. У каждого сервиса обязательны лимиты `cpus`/`memory`/`pids`, `cap_drop: [ALL]`,
   `no-new-privileges`, `read_only` (исключения — в `WRITABLE_ROOTFS` с обоснованием).
7. **Окружение изменяется только через `make container-up`**, который сначала выполняет
   `container-check` и не запускает `docker compose up` при нарушениях. В PR с изменением
   `Dockerfile`, `docker-compose.yml`, `nginx/` или зависимостей прикладывается вывод
   `make container-check`.
8. Изменение политики (`PUBLIC_PORTS`, `WRITABLE_ROOTFS` и т. п. в `scripts/container_check.py`)
   — только отдельным PR с обоснованием и одобрением второго участника.

## Правила CI (Lab 5)

1. В `main` попадают только PR: прямой push, force-push и удаление ветки запрещены
   набором правил `main-protection` (`.github/rulesets/main.json`).
2. Для слияния нужны все зелёные стадии CI и `guard`, одобрение второго участника и,
   если затронуты критические файлы, — **владельца кода** (`.github/CODEOWNERS`).
3. Страж (`scripts/ci_guard.py`, запускается из `main`) блокирует удаление тестов,
   пропуск тестов, отключение проверок, снижение порогов и ослабление правил
   анализаторов и pipeline. Осознанное ослабление — только с меткой
   `acknowledged-weakening`, которую ставит владелец кода, и с обоснованием в PR.
4. Исключения уязвимостей (`security/vulnerability-allowlist.toml`) — только с
   причиной, мерами защиты, сроком и одобрившими; просроченное исключение роняет CI.
5. Пароли и токены — только в секретах GitHub Actions, никогда в файлах репозитория.

## Правила поставки (Lab 6)

1. На staging попадают только образы из registry, прошедшие CI на `main`; на сервере
   образы не собираются. Ручной выпуск — только конкретного тега (не `latest`).
2. Выпуск засчитывается, только если прошла проверка работающего релиза
   (контейнеры, служебный адрес, версия, основной сценарий); иначе он красный,
   а предыдущая версия возвращается автоматически.
3. Миграции БД — обратно совместимые: возврат версии не откатывает схему.
4. Настройки и секреты окружения — только в `/srv/auctions-staging/staging.env`
   на сервере, не в репозитории и не в образе.
